## Формат датасета

### Структура файлов

Датасет хранится в виде папки со структурированными файлами.

❗️ В репозиторий выкладываются только некоторые файлы, в структуре ниже они отмечены восклицательным знаком. Это файлы, документирующие датасет и его параметры. Остальные файлы, хранящие сам датасет, будут загружены только на Hugging Face Hub (это [следующий этап](#следующий-шаг)).

Структура папки:

```
dataset_name (название датасета)/
├── !README.md!  # документация (англ)
├── !README_ru.md!  # документация (рус)
├── !dataset_meta.json!  # метаинформация
├── test.json  # основные вопросы теста (не класть в репо, только на HF)
└── shots.json  # вопросы для few-shot примеров (не класть в репо, только на HF)
```

>### Ниже приведены подробные описания формата файлов, для примера можно ориентироваться на [готовые датасеты](../datasets).

Все вопросы датасета хранятся в двух файлах:
- `test.json` — основные вопросы теста
- `shots.json` — вопросы-примеры для few-shot режима (❗️не должны повторять ни вопросы, ни медиа из основного теста❗️)

Структура файлов:

```json
test.json
{
    "access": "", //"private" у приватного датасета, "public" у публичного
    "data": [
        // вопросы датасета, их структура описана ниже (см. Структура вопросов)
    ]
}
```

```json
shots.json
{
    "data": [
        // вопросы датасета, их структура описана ниже (см. Структура вопросов)
    ]
}
```

### Структура вопросов

В этом разделе рассмотрена структура вопросов, хранящихся в поле `data` файлов `test.json` и `shots.json`. Описание каждого поля приведено ниже.

```json
{
    "instruction": int, // int в исходном файле датасета, str при загрузке на HF Hub
    "inputs": {
        "question": str,
        "option_a": str,
        "option_b": str,
        "option_c": str,
        "option_d": str
    },
    "outputs": str,
    "meta": {
        "id": int,
        "categories": dict
    }
}
```


#### `instruction` — промпт-инструкция

Индекс одного из заданных для датасета промптов с плейсхолдерами. Промпты хранятся в метаданных датасета в поле `prompts`. Подробно о подготовке промптов написано [здесь](#как-оформлять-промпты).

На следующем этапе, когда датасет будет выгружаться в HF Hub, по этому индексу промпт будет вставлен автоматически из списка в метаданных датасета в поле `prompts`. Таким образом, если в дальнейшем потребуется внести изменения в формулировки промптов, менять их нужно только в метаданных, а затем заново выгружать датасет.

❗️Промпты должны быть равномерно распределены по вопросам датасета.


#### `inputs` — входные данные для вопроса

Словарь с полями, набор которых должен соответствовать набору плейсхолдеров в соответствующем промпте.

##### `question` — текстовый вопрос


##### `option_*` — варианты ответа

Варианты ответа в вопросе не обязательны, используются только если это предполагает формат задачи.

Нумеруются строчными буквами латинского алфавита ("option_a", "option_b", ...). Допускается разное количество вариантов ответа в вопросах датасета, при условии что это количество сбалансировано по датасету в целом — например, половина вопросов бинарные и половина с выбором из 4 вариантов.


#### `meta` — метаинформация об элементах вопроса

В это поле включается вся сопровождающая информация к вопросу и используемым в нем мультимодальным элементам. Эта информация ни в коем случае не используется в самом вопросе и промпте, а нужна для анализа статистик датасета и детальной оценки ответов моделей. Если какое-то поле может давать потенциальный ключ к ответу (например, в метаинформации есть поле с hints для CoT), это нужно указать в описании поля в метаинформации.


##### `id` — номер вопроса

Вопросы нумеруются с 1, нумерация сквозная для всех вопросов, **включая вопросы для shots**.

##### `categories` — классифицирующие поля

Словарь, в который входят все размеченные домены, поддомены, типы, классы вопросов и т. д. Отдельное поле на каждую категорию, со значением для конкретного сэмпла.


##### Другие поля

Внутри  `meta` можно добавлять любые другие поля.


## Документация датасета

Документация состоит из двух частей:

* текстовые описания: постановка, мотивация создания датасета и детальная методология на русском и английском языках;
* метаданные: JSON с формальными характеристиками датасета.

Файлы должны соответствовать требованиям к формату json, таким как отсутствие trailing commas и trailing whitespaces. Отступ (indent) – 4 символа, ensure\_ascii=False (файл должен быть человекочитаемым).

>### Ниже приведены подробные описания формата файлов, для примера можно ориентироваться на [готовые датасеты](../datasets).


### Текстовые описания

Текстовые описания содержат подробную документацию задачи на русском и английском языках: постановку, мотивацию создания датасета, детальную методологию создания датасета.

Каждый из двух файлов должен содержать словарь с заголовками и текстами следующих разделов документации:

| Поле ru | Поле en | Описание поля |
| :---- | :---- | :---- |
| Описание задачи | Task description | Описание датасета с кратким саммари по мотивации и методологии создания. Самая основная информация, сопроводительный текст к датасету. |
| Мотивация | Motivation | Этот раздел должен разносторонне отвечать на вопрос "зачем эта задача?". Вопросы для ориентира: \- На оценку каких моделей ориентирован этот датасет? Для каких моделей он НЕ подходит (limitations)? \- На каких пользователей ориентированы результаты оценки на данной задаче? Как эти пользователи будут интерпретировать результаты, полученные при оценке на этом датасете? \- Какие способности моделей оценивает задача? Что подразумевается под этими способностями? Не просто language understanding, а что именно и в какой постановке. Зачем оценивать именно эти способности? \- Как устроены вопросы в датасете, и почему они устроены именно так? Как понять, что именно такой дизайн задачи оценивает те способности моделей, которые нужно оценить? Валидность эксперимента. \- Как выбраны метрики (особенно когда метрика не просто доля правильных ответов) и почему они именно такие? Как такой выбор метрик помогает пользователю интерпретировать результаты? |
| Создание датасета | Dataset creation | Подробное описание методологии сбора датасета, источников данных, отбора данных, процесса валидации вопросов. |
| Human baseline | Human baseline | Подробное описание методологии проведения human baseline ([инструкция](human_baseline.md)). |
| Авторы | Contributors | Список строк-имен разработчиков датасета в формате "Имя Фамилия". |

Формат разделов:  
```json
{
    "Заголовок раздела 1": "текст раздела\nсо\nвсеми\nпереносами",
    "Заголовок раздела 2": "текст с\n\n### вложенными\nзаголовками"
}
```

**Добавление верхнеуровневых полей помимо перечисленных в таблице не предусмотрено**. Внутри разделов можно использовать любую структуру в формате MD с подзаголовками уровня "\#\#\# Заголовок" и ниже. Формат: ровно 1 пустая строка (`\n\n`) между заголовком и телом раздела, не более одной пустой строки внутри раздела.


### Метаданные датасета

Метаданные содержат словарь с формальными признаками датасета, используемыми для карточки датасета.

❗️ Этот файл — "истина в последней инстанции" по датасету. В нем должны отражаться все вносимые изменения. Например, название датасета во всех случаях берется именно из файла с метаданными.


| Название поля | Описание поля |
| ---- | ---- |
| `dataset_name` | Название датасета. Пишется в CamelCase или CAPITALS, за исключением случаев адаптации других датасетов для русского языка – в этом случае называются в виде ruCamelCase / ruCAPITALS. |
| `description` | Короткое описание задачи (на английском языке), общая идея (максимум 200 символов). |
| `license` | Для публичного датасета: лицензия на материалы из оригинального датасета. Даже если из него переиспользована только часть (например, только картинки или только вопросы), лицензия все равно должна сохраняться. Формат: строка с md-форматированием, то есть если у лицензии помимо названия есть страница с описанием, пишем в виде \[license name\](url). Для приватного датасета: "MERA\_private". |
| `dataset_size` | Количество вопросов в датасете. |
| `domains` | Домены датасета в случае разделения на домены-папки, иначе пустой список. |
| `synt_source_models` | Список моделей, которые были использованы при генерации текстовых и мультимодальных материалов для вопросов бенчмарка. |
| `data_example` | Пример данных из оформленного по [инструкции](#структура-вопросов) датасета с точным соблюдением формата и набора полей. Пример не должен дублировать никакие вопросы из основного теста. |
| `data_field_descriptions` | Описания полей `data_example` с указанием типов данных. Описание для каждого поля на русском и английском в формате `{"field_name": {"en": "Description.", "ru": "Описание."}}`. |
| `prompts` | Промпты с плейсхолдерами. Набор плейсхолдеров в каждом промпте должен соответствовать набору полей в `data_example["inputs"]`. В общем случае промптов должно быть не менее 5. В случае датасетов с доменами — не менее 5 промптов на каждый домен. [Как оформлять промпты?](#как-оформлять-промпты) |
| `metrics` | Словарь из названий и описаний метрик, используемых для оценки. |


## Как оформлять промпты

Для каждого датасета необходимо подготовить 5 промптов. По умолчанию все задачи оцениваются в zero-shot сетапе. Если для вашей задачи необходимо указать формат с помощью шотов, то вы можете добавить их.

Промпт задается в виде строки с плейсхолдерами. Набор плейсхолдеров должен в точности соответствовать набору поле в поле `inputs` вопросов датасета. Текстовые плейсхолдеры (то есть куда будут вставляться текстовые элементы) пишутся в фигурных скобках {} (`{question}`).

Промпты необходимо офрмить по принципу Semantic Anchor Prompting (SAP).

SAP разделяет промпт на два независимых слоя:

| СЕМАНТИЧЕСКИЙ СЛОЙ (стабильный) | СЛОЙ РАЗДЕЛИТЕЛЕЙ (изменяемый) |
|--------------------------------|--------------------------------|
| • Состав блоков (какие блоки)<br>• Порядок блоков<br>• Содержание каждого блока<br>• Спецификация формата ответа<br>• Наличие/отсутствие фью-шотов<br>• Политика по вызову ризонинга | • XML-теги<br>• Markdown-заголовки<br>• Текстовые метки<br>• Только переносы строк<br>• Смешанный формат |

Семантический слой определяет что именно говорит промпт. Слой разделителей определяет как визуально отделяются блоки. Только слой разделителей должен меняться при изменении стандартов форматирования.

### Семантический слой SAP

Каждый промпт бенчмарка состоит из фиксированного набора семантических блоков. Не все блоки присутствуют в каждом промпте — только те, что относятся к задаче. При необходимости, вы можете добавить блоки, не указанные в таблице ниже и необходимые для вашей задачи:

| Блок | Роль | Обязателен? |
|------|------|--------------|
| Задача<br>{task_formulation} | Инструкция с глаголом действия в начале (Классифицируй, Извлеки, Реши, Напиши...) | Всегда |
| Контекст<br>{context} | Фоновая информация, данные, отрывок, таблица или предметные ограничения | Когда задача требует внешних данных |
| Примеры | Одна или несколько пар вход→выход, демонстрирующих ожидаемый формат | Когда формат не очевиден или нужны фью-шоты |
| Формат ответа<br>{format_description} | Явная, позитивная, где возможно числовая спецификация формата | Всегда |
| Вопрос<br>{question} | Конкретный вопрос или входные данные, на которые нужно ответить | Всегда |
| Варианты ответа<br>{option_1...option_n} | Варианты ответов для MCQ, список допустимых меток и т.д. | Когда задача имеет перечисленные варианты выбора (MCQ) |

### Слой разделителей SAP

SAP не предполагает единый формат разделителей для всех задач. Вместо этого определяется политика выбора разделителя в зависимости от типа задачи:

| Сложность задачи | Выбор разделителя | Обоснование |
|------------------|-------------------|--------------|
| Простая (2–4 блока: Задача + Вопрос, или Задача + Формат + Вопрос + Варианты ответа) | Обычный текст разделенный двойными переносами строки ```\n\n``` | Минимальные накладные расходы; отсутствие зависимости от специфического формата; читаемо человеком; эффективно по токенам |
| Средняя (5 блоков: к простой формулировке добавляется еще один блок, например с внешними данными) | Легковесные метки: Задача:, Контекст:, Формат:, Вопрос: с последующим переводом строки | Однозначные границы блоков без тяжёлой разметки; совместимо с разными моделями; читаемо человеком |
| Сложная (6+ блоков или вложенные данные, такие как таблицы/JSON/код внутри Контекста: требуется явное разделение блоков, иначе можно запутаться, где и какой) | XML-теги: `<task>`, `<context>`, `<format>`, `<question>` | Однозначные начальные и конечные границы предотвращают путаницу содержимого с разделителями; все основные семейства моделей работают с XML; явная вложенность обрабатывает сложные данные |

### Правила формата SAP

- Позитивные, а не негативные инструкции: «Отвечай только буквой A, B, C или D» вместо «Не добавляй никаких объяснений». Если уже сказали выдать одну букву, то должно быть очевидно, что ничего, кроме этой одной буквы, в ответе быть не должно.
- Конкретные и численные: «Напиши ровно 3 предложения» вместо «Будь краток». Больше конкретики, чисел, меньше абстракций (по возможности и без подсказок).
- Включайте префикс завершения (триггер ответа): допускается добавлять префикс к генерации модели, например, "Ответ:", который должен заставить можель дать ожидаемый ответ.
- Помещайте формат непосредственно перед вопросом: Никогда не закапывайте формат в середине контекста (lost-in-the-middle). Формат не "главнее" самого тестового вопроса, потому следует прямо перед ним, но не после.
- Для MCQ: Используйте формат "Ответ: X" (одна буква) как пример. Используйте, например, паттерн Последняя строка твоего ответа должна быть в следующем формате: 'Ответ: X'.
- Для свободной формы: Используй \boxed{} для математики, тройные обратные кавычки для кода или другие доменные стандартные контейнеры.
- Для сложных/новых форматов: Предоставьте один пример в блоке "Примеры". Никогда не полагайтесь исключительно на словесное описание, когда формат не является типичным (число/буква/фраза). Всегда даем пример, чтобы убрать возможную неоднозначность в описании.
- Однозначный формат ответа: Формат ответа пишется так, чтобы не создавать неоднозначности, не допускать иных трактовок, а также он должен быть понятным.

### Пример валидного промпта

```
Задача:
Решите пример на сложение

Контекст:
Примеры содержат только положительные числа

Формат ответа:
Укажите только число после символа =

Примеры:
3+3=6

22+22=44

Вопрос:
2+2=
```
